# FleetOps Command Center — SIH26137

A frontend prototype for **SIH26137: Quantum-Inspired Intelligent Traffic Route
Optimization in Transportation Systems Using Metaheuristic Optimization**
(problem statement by Egreen Quanta).

This is a dark-themed "autonomous fleet operations command center" dashboard
that demonstrates the *shape* of a QPSO-driven multi-vehicle route
optimization system: a simulated road network, dynamic traffic events, a
metaheuristic optimization engine with a convergence chart, before/after
comparisons, algorithm benchmarking, and a scripted end-to-end demo.

**Everything in this app is simulated client-side.** There is no backend, no
map/API key, and no real traffic or GPS data — see [Prototype
limitations](#prototype-limitations) below.

## Installation & running locally

```bash
npm install
npm run dev
```

Then open [http://localhost:3000](http://localhost:3000). No environment
variables or API keys are required.

To type-check, lint and build for production:

```bash
npx tsc --noEmit
npm run lint
npm run build
```

## How the simulated QPSO works

`lib/simulation/qpso.ts` does **not** run a real particle-swarm optimization
against live traffic data. It is a deterministic mock designed to produce a
plausible, realistic-looking convergence curve and result set for demo
purposes:

- The **judge-demo scenario** (42 deliveries, 8 vehicles, clean baseline) is
  hardcoded: a Dijkstra baseline of 142 min / 84.2 km / ₹2,840, improving to
  108 min / 71.4 km / ₹2,210 under "QPSO". A second hardcoded outcome models
  re-optimization after a major congestion event (recovers to ~116 min —
  better than the degraded state, short of the clean-network optimum).
- For **custom runs** (when the user changes population/iterations/weights
  in the Optimization panel), results are derived algorithmically from the
  baseline using the objective weights and population/iteration settings, so
  the panel feels responsive without being purely random.
- The **convergence curve** (`genConvergence`) is generated by an
  exponential-decay function from a start fitness to an end fitness, with a
  small seeded noise term layered on top so it looks like a real optimizer's
  fitness trace (fast early improvement, diminishing returns, minor
  jitter) rather than a straight line.
- The **optimization log** (`OPTIMIZATION_LOG_STEPS`) is a scripted sequence
  of status strings ("Initializing quantum particle population...",
  "Iteration 150/200...", "Optimization complete.") stepped through with
  `setTimeout` over ~2.6–3.6 seconds — it does not run 200 real iterations.
- All "randomness" (benchmarks, experiment history, scalability data, fleet
  generation) uses a seeded PRNG (`mulberry32`) so numbers are stable across
  re-renders instead of flickering, while still varying between different
  seeds/inputs.

The Benchmarks and Experiments pages are explicitly labelled "Simulated /
illustrative prototype data — not measured experimental results."

## Demo Mode

The top bar's **Demo Mode** control (Start / Pause / Restart) drives a real
state machine (in `SimulationProvider`) through 10 steps — loading the
network, showing the fleet, running the baseline, running QPSO, showing the
improvement, injecting a congestion incident, detecting degradation,
re-optimizing, showing recovered routes, and showing the benchmark
comparison — navigating across pages with `next/navigation`'s `router.push`
and firing the same context actions a user would trigger by hand
(`runOptimization`, `injectIncident`, `reoptimizeFleet`). Progress is shown
as a step list with a live step counter in the top bar.

## Prototype limitations

- The road network (`lib/simulation/routes.ts`) is a fixed, illustrative
  topology (1 depot, 1 hub, 20 delivery points, 2 checkpoints) drawn on a
  static SVG coordinate grid — it is not a real city map and does not use
  MapLibre, Google Maps, or any mapping API.
- QPSO is mocked, not implemented — see above.
- Benchmark and scalability numbers are illustrative, generated from
  hand-tuned relative-performance profiles per algorithm, not measured runs.
- Vehicle/delivery state (positions, battery, ETAs) is generated once per
  session from a seeded RNG and does not simulate continuous physical
  motion; the map shows discrete node/edge state and a highlighted "active"
  route rather than moving vehicle icons along the path in real time.
- There is no persistence — refreshing the page resets all state to its
  seeded defaults.

## Swapping in a real backend

The intent is that `lib/simulation/*` can be replaced by calls to a real
optimization service (e.g. a FastAPI backend) with minimal disruption to the
UI layer:

1. Keep the TypeScript interfaces in `lib/simulation/types.ts` as the
   contract between frontend and backend (or generate them from an OpenAPI
   schema).
2. Replace the body of `runQPSO()` in `lib/simulation/qpso.ts` with a
   `fetch`/`POST` to a backend endpoint (e.g. `POST /api/optimize`) that
   accepts `{ population, iterations, weights, constraints }` and returns
   `{ result, convergence, baseline }`. The calling code in
   `contexts/simulation-context.tsx` (`runOptimization`) already treats this
   as an async operation driven by a progress/log sequence, so it can be
   adapted to poll a job endpoint or subscribe to a WebSocket/SSE stream for
   real iteration-by-iteration progress instead of the simulated `setTimeout`
   log.
3. Replace `lib/simulation/routes.ts`'s static graph with a real road network
   loaded from a backend (GeoJSON or a graph database), and swap the SVG map
   for a real mapping library (e.g. MapLibre GL) once real coordinates are
   available — the `NetworkMap` component's props (`edges`, node list) are
   already the natural seam for this.
4. Replace `lib/simulation/traffic.ts`'s synthetic event injection with a
   live traffic feed or a backend endpoint that returns real
   `TrafficEvent[]` objects.
5. `lib/simulation/benchmarks.ts` and `experiments.ts` can be replaced with
   endpoints that return real algorithm comparison runs and a persisted
   experiment log (e.g. backed by a database), respectively.
